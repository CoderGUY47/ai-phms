🩺 AI-PHMS (AI-Powered Prescription & Health Analytics Management System)
================================================================================
Interview Preparation Guide & Technical Architecture Breakdown
================================================================================

This document outlines the core architecture, portal design, data workflows,
and key technical decisions of the AI-PHMS project. Read this to answer project-
related questions in technical interviews.

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW & ELEVATOR PITCH
--------------------------------------------------------------------------------
* Elevator Pitch:
  "AI-PHMS is a secure, client-side medical command center designed to streamline 
  patient record organization and empower doctors with real-time health histories
  before consultations. It uses AI to parse unstructured documents (like written 
  prescriptions or scan results) into structured clinical JSON, stores them 
  securely in a browser-isolated local ledger, and visualizes them on interactive
  dashboards."
  
* Tech Stack:
  - Frontend: Next.js 16 (App Router, Server Actions, API Route Handlers)
  - React version: React 19 (Concurrent features, modern Hooks)
  - Styling: Tailwind CSS 4 & Custom Vanilla CSS styles
  - UI Components: Radix UI primitives & Shadcn UI (modified border-radius)
  - Charts: Recharts (responsive pie, area, and bar charts)
  - Icons: Lucide React (standardized visual indicators)
  - TypeScript: Strict type-safety across all data interfaces

--------------------------------------------------------------------------------
2. DATA SCHEMA & TYPE SAFETY
--------------------------------------------------------------------------------
The project enforces strict TypeScript interfaces to guarantee that the parsed 
AI JSON outputs match our UI components.

* Key TypeScript Interfaces:
  - MedicalRecord:
    - recordId: string (Unique ID)
    - date: string (Consultation date)
    - doctorName: string (Attending physician)
    - patientCase: string (Diagnosis/symptom summary)
    - respiratoryRate: string (Pulmonary vitals)
    - medicines: Medicine[] (Structured list)
    - testResults: TestResult[] (Diagnostic lab values)
  - Medicine:
    - name: string
    - dosage: string (e.g. "1-0-1")
    - duration: string (e.g. "7 days")
    - classification: string (e.g. "Antibiotics", "Vitamins", "Gastric")
  - TestResult:
    - testName: string
    - value: string (Numerical score/rating)

--------------------------------------------------------------------------------
3. THE PORTALS & WORKFLOWS
--------------------------------------------------------------------------------
The project is segmented into three primary portals accessible via a beautiful 
navigation menu:

* PORTAL 1: Patient Portal (Document Ingestion)
  - Document Upload Center: Clean drag-and-drop zone supporting images (PNG, JPEG) 
    and PDF files.
  - AI Processing Engine: File uploads trigger a Server Action middleware connected 
    to the Gemini/OpenAI API. A detailed system prompt instructs the AI to read 
    the document and output ONLY a structured JSON string matching the 
    TypeScript interface (`MedicalRecord`).
  - Local Ledger Storage: The extracted JSON is saved securely in the browser's 
    `localStorage`, organized date-wise under the patient's record profile.

* PORTAL 2: Doctor Portal (Clinical Analytics)
  - Search Index: Allows doctors to instantly lookup patient records by ID/Name.
  - Antibiotic Tracker: Critically tracks the patient's lifetime exposure to 
    antibiotics to prevent over-prescription risks.
  - Vitals & Lab History: Chronological trends of vital signs and test values.
  - Deep-Dive Dialogs: Modal popup overlays displaying the complete original details 
    of any single consultation date.

* PORTAL 3: Admin Portal (System Auditing)
  - Directory Control: Mock-register new patients/doctors, activate, suspend, 
    or delete profile credentials.
  - Audit logs: Ledger tracking document uploads, API calls, and administrative 
    profile status changes.
  - Seed Control: Purge browser local storage or reload mock seed datasets.

4. INTERACTIVE DASHBOARD ARCHITECTURE (page.tsx Refactoring)
--------------------------------------------------------------------------------
The landing dashboard is built on a highly modular grid structure. We refactored 
this page to separate data-retrieval from rendering:

* API Integration:
  - Instead of hardcoding datasets in the client file, we built a Route Handler 
    at `/api/dashboard/route.ts` to serve dynamic stats.
  - `page.tsx` fetches from this API using `fetch().then()` inside a `useEffect` 
    hook on mount.
  - Dashboard states are passed down to independent components as props.

* Segmented Components:
  - BioDataChannels & NeuralAnatomyRadar: Sync with each other. Clicking on an 
    organ button in the list updates the `selectedOrgan` state, which causes 
    the anatomical diagram to highlight the organ and load its specific vitals 
    and synthetic AI diagnostic text.
  - CaloricPerformance & TherapeuticEngine: Visualize nutrition trends and target 
    compliance rate (e.g. compliance circle compliance meter).
  - DepartmentStatistics & LiveTriage: Chart doctors vs. patients across departments 
    and track live triage severities (Emergency, Urgent, Routine).
  - PrescriptionIngestionFeed: Displays real-time parsing statuses.
  - ActiveConsultationCard & CalendarWidget: Manage selected calendar days and 
    schedules.

5. TOP INTERVIEW QUESTIONS & ARCHITECTURAL DISCUSSIONS
--------------------------------------------------------------------------------

Q1: Why did you use browser localStorage instead of an external database?
A1: "For this frontend analytics prototype, `localStorage` acts as a self-contained, 
     zero-latency client ledger. It guarantees complete privacy (no clinical patient 
     data leaves the client machine) and ensures high speed. In production, this ledger 
     would sync with a HIPAA-compliant database (like Google Cloud Spanner or Firestore) 
     via GraphQL or REST endpoints."

Q2: What is the hydration mismatch issue you solved, and how?
A2: "Chrome's Autofill prediction feature dynamically injects attributes like 
     `autofill-information` and `autofill-prediction` into `<input>` tags on the 
     client right after page load. Because Next.js server-renders (SSR) clean tags, 
     React detects a mismatch during client hydration and throws console warnings. 
     I resolved this by adding `suppressHydrationWarning` to the filter input. This 
     instructs React to ignore extension-injected client attributes while mounting."

Q3: How do you ensure the AI outputs valid structure?
A3: "We utilize structured AI outputs. By defining a strict JSON Schema inside our 
     AI API system prompts, we force the AI Model (e.g., Gemini) to respond in a 
     JSON shape that maps exactly to our TypeScript interfaces, avoiding unparseable 
     conversational responses."

Q4: How did you optimize Dashboard performance and maintainability?
A4: "The initial implementation had over 1,100 lines of code in a single file with 
     hardcoded data arrays. I refactored it by:
     1. Creating a Next.js Route Handler (`/api/dashboard`) to serve stats dynamically.
     2. Segmenting the main layout into 12 self-contained, reusable components in the 
        `src/components/dashboard` directory.
     3. Passing dynamic data and state updates down through typed React Props. 
     This reduced the primary layout file by over 80% and improved scannability."
